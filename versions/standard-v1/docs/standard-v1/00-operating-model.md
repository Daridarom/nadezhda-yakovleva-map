# Standard v1 — ролевая операционная модель AI Штаба

## Зачем
Штаб работает не вокруг конкретной модели (ChatGPT, Claude, Codex, Hermes), а вокруг устойчивых ролей, артефактов и критериев перехода. Модели можно менять; процесс и ответственность должны сохраняться.

## 10 рабочих ролей
1. **Business Analyst** — понимает процесс, пользователя, проблему и точку эффекта AI.
2. **Documentalist / Context Engineer** — превращает разговоры и источники в Project Intake, Spec, Blueprint, decision log и контекст-пакет.
3. **AI / Product Architect** — проектирует целевую систему, роли, права, интеграции, риски и acceptance criteria.
4. **Builder** — собирает код, агента, workflow или автоматизацию вертикальными срезами.
5. **Platform Integrator** — соединяет API, MCP, GitHub, базы, хостинг и сервисы; отвечает за зависимости и health checks.
6. **Creative / Product Director** — управляет смыслом, иерархией и вниманием; решает, что оставить, убрать и усилить.
7. **QA / Red Team** — независимо проверяет результат против spec и acceptance criteria.
8. **Security / Governance** — проверяет секреты, permissions, data flows, prompt injection, supply chain и внешние skills/MCP.
9. **Release / Ops** — preview, smoke-tests, production, monitoring и rollback.
10. **Knowledge Steward** — обновляет STATE/DECISIONS/RADAR и закрывает устаревшие решения, чтобы следующий цикл начинался с актуальной правды.

## Контракт передачи между ролями
Каждая роль должна передавать следующий пакет:

- **INPUTS** — на каких фактах и артефактах работала;
- **DECISIONS** — какие решения приняты и почему;
- **OUTPUT** — конкретный артефакт, а не пересказ;
- **UNKNOWN** — что осталось неизвестным;
- **RISKS** — риски/ограничения;
- **NEXT** — что именно должна сделать следующая роль.

Если пакет неполон, следующая роль не должна молча додумывать критические данные.

## Двухключевой принцип
Для production-критичных результатов автор и единственный проверяющий не должны совпадать.

Примеры:
- Builder ≠ единственный QA;
- Integrator ≠ единственный Security reviewer;
- Creative Director ≠ единственный человек, подтверждающий факты;
- Release требует PASS + явное human approval для необратимых действий.

## Уровни сложности
Полный процесс нужен не всегда.

- **L0 — микро-задача:** ответ, текстовая правка, локальная идея. Без полного pipeline.
- **L1 — небольшая обратимая правка:** spec-lite → Builder → QA.
- **L2 — полноценный проект/редизайн:** полный ролевой pipeline.
- **L3 — высокий риск:** полный pipeline + усиленный Security/Governance + обязательные human approvals + rollback/monitoring.

Цель — не бюрократия, а соответствие глубины контроля масштабу и риску.

## Применение к сайту Надежды
Пилот относится к **L2**.

Текущий маршрут:
1. Business Analyst — выполнено через Project Intake.
2. Documentalist — выполнено: Intake + Blueprint + decisions.
3. AI/Product Architect — выполнено: структура, компоненты, gates, risks.
4. Builder — следующая стадия: visual iteration на отдельной ветке.
5. Platform Integrator — минимальный: GitHub Pages, внешние документы, Telegram, карты.
6. Creative/Product Director — hero A/B/C, ритм страницы, motion hierarchy.
7. QA/Red Team — повторная независимая приёмка.
8. Security/Governance — внешние зависимости, ссылки, отсутствие секретов/лишних trackers.
9. Release/Ops — preview → smoke tests → merge → post-deploy check.
10. Knowledge Steward — обновить итоговые решения и lessons learned после релиза.

## Definition of Done для самого стандарта
Standard v1 считается рабочим, если новый агент/чат может открыть артефакты проекта и без чтения длинной истории ответить:
- что мы создаём;
- для кого и зачем;
- что уже решено;
- что ещё неизвестно;
- кто/какая роль сейчас отвечает за следующий шаг;
- какие действия требуют подтверждения;
- по каким критериям результат будет принят.
